# Library architecture scheme — O1

Evidence is limited to consumer instructions and the read-only handbook H, pinned to `1c9deb1558b9d50737d6979dabab308350468c67`. Revision provenance is the controller's archive receipt, not an independently resolved Git HEAD. There is no application, schema, stack, test suite or deployment to inspect. All artifacts and checks below are proposed.

**Requirements:** Onion backend; classic interactive MVC browser; persisted loans; authorized librarian input; maximum three active loans per member; one active loan per copy; refusal of renewal when another member has a hold. **Conventions:** layer-first paths, capability public entries and separated source/runtime/composition accounts follow H. **Design inferences:** one process-facing backend and transactional database, a browser screen for librarian circulation, the proposed names/contracts and locking algorithm. A relational database is a conditional fit, not an approved vendor/version.

“Active” means issued and not returned. Assume a hold covers a title and renewal considers active holds on that title, excluding the borrowing member; title-versus-copy hold scope requires product confirmation before implementation. Renewal duration, due-date calculation, late-loan restrictions and additional renewal limits are unspecified: `LoanTerms` must receive an approved policy rather than invent these rules. No member self-service permission is assumed.

## Contracts, rules and restoration challenge

`IssueLoan({memberId,copyId,requestId}, principal)` returns a committed LoanSummary or `member-limit/copy-unavailable/forbidden/not-found/unavailable`. `RenewLoan({loanId,expectedRevision,requestId}, principal)` returns a committed summary or `inactive/held-by-other/stale/forbidden/not-found/unavailable`. Return similarly requires identity, revision and request ID; reads are authorized and return only needed member/copy/title/due-date/status fields. Principal comes exclusively from verified credentials; payload identifiers identify targets, never grant permission.

`CirculationTransaction.run(actor,requestIdentity,fingerprint,work)` supplies transaction-scoped repositories and facts: load loan; count member active loans; find copy occupancy; obtain active hold-owner IDs for the relevant title; save with expected revision; record result. Repository `find/insert/save` returns domain objects or known conflicts; `LoanReader` returns summaries. The operation owns when the transaction begins/commits; the adapter owns driver details. `AccessPolicy.requireCirculation(principal,member,copyOrLoan)` checks librarian capability and actual resource access, including target associations, inside the operation. Trusted principal is not a permission bypass for non-HTTP callers.

**Renewal alternatives:** entity `Loan.renew({hasOtherMemberHold,newDueDate})` keeps transition and eligibility together, but the entity cannot discover current holds; the supplied fact's freshness is still Application's obligation. A pure `RenewalPolicy.decide(loanFacts,holdFacts,terms)` fits behavior involving Loan and other members' holds, at the cost of one additional collaboration. Choose the latter for cross-object eligibility, followed by `Loan.renew` for the active-state/date transition. No duplicate hold rule in both places. Needed facts include borrower, title/copy identity, active status, current due date, approved terms, other active hold ownership and current stored revision. Application obtains them in one protected transaction. Basis: H `architecture/foundations/domain-modeling/README.md`, **Decisions owned by one object**, **Decisions involving several facts**, **Obtaining facts and completing work**.

**Reject ORM imports in Domain, including type-only imports.** `mapStoredLoan` translates ORM state into domain-owned `LoanSnapshot`; `Loan.restore(snapshot)` checks structural/domain consistency and preserves stored identity/status/dates/revision, without issuing a new loan or applying today's issuance eligibility to history. Invalid stored state becomes an integration/data-integrity failure, not a fabricated active loan. Cost is explicit mapping; benefit is independent rules and replaceable storage. H `architecture/foundations/code-placement.md`, **Parsing and mapping follow the boundary**, and `architecture/foundations/dependency-boundaries.md`, **External technology types stop at the boundary**, directly support this correction.

## Separate source, startup and runtime

Permitted source imports: operations → domain and own ports; database adapter → ports/domain; HTTP handler → public Application entry; View/Controller → public Model contract; Model → browser Application gateway contract. Forbidden: Domain → ORM, Application → database adapter, browser Model/View → HTTP implementation, any inner module → bootstrap. Public entries deliberately omit private mapping/locking helpers. Basis: H `architecture/foundations/module-boundaries-and-public-apis.md`, **Public API per non-trivial module**, **Barrels are contracts, not export dumpsters**.

At startup each executable imports concrete adapters and supported factories and supplies objects manually. At runtime Model calls the supplied HTTP gateway; handler calls RenewLoan; RenewLoan calls the supplied transaction adapter/repository. Ports are descriptions, not forwarding objects. These runtime outward calls do not authorize outward imports. Basis: H `architecture/foundations/composition-root.md`, **Composition is a boundary, not business policy**, **A DI container is optional**.

## Operation, failure and browser-state trace

1. View forwards Renew to Controller, which invokes Model with the selected loan/revision. Model retains an immutable intent/request ID, enters pending and notifies Views; duplicate submits for that loan are disabled.
2. Gateway sends proposed `POST /loans/{id}/renewals` with request ID and expectedRevision. Backend parses, verifies session and CSRF protection for cookie credentials, then passes trusted context. Malformed input returns 400; unauthenticated 401; forbidden 403 or consistently concealed 404. No storage mutation occurs.
3. Operation authorizes resource access and opens the transaction. Proposed initial implementation serializes circulation writes using one database guard row locked until commit. Every issue, return, renewal and hold creation/removal must acquire it; otherwise the design is invalid. It then rereads current facts. This trades throughput for inspectable consistency; later finer locks require renewed race analysis.
4. Issue checks member count and copy occupancy; renewal evaluates current holds and active state, then revision. A database uniqueness constraint on active copy loans backs occupancy. Member-limit and hold races are protected by the shared transaction guard, not by isolated prechecks. No external I/O occurs while locked. Refusal rolls back; conflicts return 409 with stable reason codes.
5. Save and request receipt commit atomically; success is returned only afterward. Receipt uniqueness is scoped to actor + operation + request ID; fingerprint includes target, intent and expected revision. Same key/body replays the committed result after reauthorization; different body returns conflict. Concurrent duplicates serialize and replay. A documented initial 24-hour retention permits retries within that window; older requests require reconciliation, not blind new-key resubmission.
6. Adapter rollback on known failures produces safe unavailable/conflict outcomes. Lost connection around commit is unknown, never asserted rollback. Model shows “outcome unconfirmed,” retains the key and offers same-intent retry/reconciliation. Receipt lookup/replay resolves whether commit happened. A fresh attempt after a known rejection uses a new key.
7. On confirmed success Model replaces records/revision and notifies; Views reread and render confirmation. Refusal preserves records and announces reason; stale revision triggers refresh and explicit reconsideration. Selection lives in Model for screen lifetime; form draft belongs to LoanForm, URL contains only navigable selection. Read sequence tokens prevent older responses overwriting later mutations/selection. Unmount unsubscribes/aborts reads; aborting a mutation never implies rollback. Initial loading, empty list, read error/retry, pending and unknown states remain distinct. Semantic buttons/forms, retained focus and live status feedback are proposed.

The shared HTTP contract is a design inference, not a REST claim. Security and retry principles come from H `architecture/api-design/security-and-tenancy.md`, **Identity and permission**, **Scope every object**, and `architecture/api-design/reliability-and-operations.md`, **Two bookings for one slot**, **Retries and duplicate requests**, **Timeouts and partial failure**. The guard and retention are proposed library mechanisms, not handbook guarantees.

## Change rehearsal and proposed checks

| Change or boundary | Observable proposed checks; none executed |
| --- | --- |
| Business rule: four loans instead of three | Change MemberBorrowingPolicy and boundary expectations; operations/callers remain stable. Three existing loans: current policy rejects fourth; two accepts third. Renew unaffected. |
| Persistence integration replacement | Replace database adapter/mapping/migrations and composition; preserve repository/transaction semantics. Restore returned loan without reissuing; corrupt status fails. Real database checks must prove durability and atomic receipts. |
| New authorized librarian CLI | Add CLI parser and executable composition; call public Application operations with verified identity. Allowed librarian succeeds; forged role/unauthorized member fails without save. No HTTP/private repository import. |
| Concurrent invariants | Two issues for one copy yield one active loan; two issues for a member with two loans yield at most three; hold-versus-renew serializes into an allowed ordered outcome. Test hold writes use the guard. |
| Unknown/duplicate outcomes | Drop response after commit; same key/body returns same result and one revision change. Concurrent duplicate behaves identically; changed payload is rejected. Transaction failure leaves neither loan change nor success receipt. |
| Domain and delivery failures | Own-member hold allows renewal; another member's active hold refuses; returned loan refuses. Malformed IDs, forbidden resources and unknown DTO fields never reach mutation. |
| MVC/integration | Model notification redraws two subscribed Views without Controller redraw; dispose stops updates. Malformed response is integration error; slow read cannot overwrite renewed record; keyboard retry retains intent and focus. |
| Structural boundaries | Permit adapter → LoanSnapshot and Controller → Model contract. Reject Domain → ORM type, Application → adapter reexport, literal dynamic outward import and cross-capability private import. Resolve aliases in source checks. |
