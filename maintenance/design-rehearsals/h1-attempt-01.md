# H1 — Support ticket architecture scheme

This is a design-only proposal for a new application: no implementation, schema, stack, tests or runtime exists. **Requirements:** authenticated analysts create and resolve tickets; subjects are nonblank; a resolved ticket cannot resolve again; HTTP and a trusted operator CLI share rules; storage is replaceable; the browser supports selection, refresh and mutations. **Decision:** retain the assigned Hexagonal backend and classic interactive MVC browser. **Conventions:** capability-owned folders and supported exports follow H. **Inferences:** the exact artifacts, operation contracts, concurrency algorithm and retry policy below are proposed application decisions.

H is the read-only export pinned to `1c9deb1558b9d50737d6979dabab308350468c67`. Provenance relies on the supplied controller receipt; this snapshot has no independently resolved Git HEAD. References below are H-relative. The three copied consumer skills were explicitly read and applied. The evidence format follows `architecture/foundations/architecture-design-review.md`, “Establish the decision and evidence” and “Describe owners and supported interactions.”

The backend needs caller and persistence independence, which Hexagonal directly protects; replacing it with simple transport/database handlers would duplicate rules across CLI and HTTP. Clean or Onion terminology would add no demonstrated benefit. MVC is a presentation collaboration, not the backend architecture or a second top-level layer system. No microservices, events, notifications, global store, DI container or persistent browser drafts are justified. Appearance/theme design is outside this case. Exact authentication provider, resource permission policy and database remain implementation prerequisites; none is invented as an existing guarantee.

The browser has no independent Domain folder: it displays recorded facts and submits intents, with no additional client business policy required. Form feedback may indicate an empty trimmed subject, but server Domain remains authoritative. Add a pure client domain helper only if reusable policy warrants it. The presentation Model is therefore not synonymous with Domain. This omission follows `architecture/foundations/dependency-boundaries.md`, “Avoid ceremonial boundaries,” and `architecture/patterns/presentation/model-view-controller/README.md`, “Important scope rule.”

Source imports follow Domain → Domain; Application → its contracts/Domain; adapters → required contracts; Presentation → supported application contracts and its own capability. Browser View/Controller additionally reference the Model's presentation API. Application never imports database adapters, DOM, HTTP handlers or composition, even through type imports. At runtime an operation calls the concrete supplied adapter; the interface is not another hop. Startup may import all necessary implementations. This distinction follows `architecture/foundations/dependency-boundaries.md`, “Do not confuse runtime flow with source dependency,” and `architecture/foundations/composition-root.md`, “Multiple composition roots.” Manual injection suffices.

The shared conceptual HTTP contract is proposed in `contracts/tickets-http.md`, with server delivery and client integration owning their respective representations. `POST /tickets` takes `{subject}` plus a create-attempt key; `POST /tickets/{id}/resolve` takes `{expectedVersion}`; `GET /tickets` and `GET /tickets/{id}` return authorized snapshots `{id,subject,status,version}`. Create returns 201; resolve returns 200 only after commit. Unknown shapes produce 400, invalid subject 422, missing identity 401, denied operation 403, inaccessible/missing item 404, already-resolved/stale version 409, temporary unavailability 503. Stable error codes distinguish those cases. These are application contract choices, not a REST claim or framework guarantee.

Application commands include a trusted actor separately from client data. `CreateTicket` accepts subject/key; `ResolveTicket` accepts ID/expected version. Results distinguish invalid subject, forbidden, not found, already resolved, stale version and unavailable; success contains the committed snapshot. `TicketAccess` checks create permission and resource-specific read/resolve access for both callers. Since no ownership/assignment rule is supplied, its precise policy needs product approval before implementation; broad “analyst” membership alone cannot silently authorize every object. Scoped repository reads/lists/saves enforce the resulting permitted resource scope. Unknown client fields cannot set actor, status or version. Credential verification belongs at entry; resource policy belongs to the capability. Cookie-based deployment additionally needs CSRF protection. Basis: `architecture/api-design/security-and-tenancy.md`, “Identity and permission,” “Scope every object” and “Other request threats”; no tenancy feature is inferred.

For a resolution, the View forwards intent; `TicketsController` captures the selected ID/version and invokes `TicketsModel.resolve`. The Model marks that ticket pending and notifies the subscribed View. Browser operation calls the injected gateway, which sends the request. HTTP verifies identity/parses input; `ResolveTicket` starts `TicketWork`, loads within permitted scope, checks access, applies `Ticket.resolve`, then conditionally saves against the loaded and expected version. The adapter atomically compares version/status and writes a new version. Exactly one competing resolution may commit; the loser returns a documented conflict after re-reading, without claiming success. Rechecking access within the work boundary avoids treating an earlier screen read as authorization. Permission changes outside that transaction require a defined authorization snapshot/revocation policy before implementation.

Persistence failures roll back and map known failures safely; unexpected defects remain internal with a correlation ID. Success crosses response mapping and client parsing into the Model, which replaces the snapshot and notifies the View. No optimistic “resolved” label precedes confirmation. Domain checks alone cannot prevent a database race. This algorithm applies the concurrency principle from `architecture/api-design/reliability-and-operations.md`, “Optimistic concurrency,” without claiming an HTTP ETag implementation.

A create request can commit before its response disappears. Proposed `TicketWork` therefore atomically stores ticket and receipt keyed by trusted actor, operation and attempt key, with a normalized-subject fingerprint. Same key/body returns the recorded result; changed body is rejected; concurrent same-key calls serialize or receive an explicit in-progress result and retry later with that key. Retain receipts 24 hours; browser and CLI retain their key for reconciliation during that window. After expiry, no automatic resubmission or duplicate-free guarantee is offered: report uncertainty for operator review. A genuinely new create gets a new key. Resolve needs no receipt for this scope: after a lost reply, retrieve the ticket; a resolved snapshot confirms current state but does not prove which caller resolved it. Never blindly treat a retry's already-resolved conflict as the first call's success. Basis: the same reliability guide, “Retries and duplicate requests” and “Timeouts and partial failure.”

The Model lasts for the mounted screen. Form draft and selection are screen-local; no URL/deep-link or cross-route persistence requirement exists. Server facts remain cached snapshots with freshness markers, cleared on identity change. Initial load distinguishes loading, empty and failure. Refresh preserves previous data marked stale and allows retry. Generation counters prevent old refresh/detail replies from overwriting newer selection or mutation results; successful mutations invalidate earlier reads before refreshing. Reads may cancel on disposal; writes may continue server-side after browser cancellation. Serialize mutations per ticket, keep create drafts on failure, and retain uncertain attempt keys. Unsubscribe and ignore late completions after disposal. Semantic buttons/forms, keyboard selection, associated errors, pending announcements and deliberate focus after success/failure belong to the View. This follows `architecture/frontend/state-management.md`, “Assign state by responsibility” and “Forms are not global state by default,” plus the design-review guide's frontend requirements.

For MVVM, replace `TicketsController` and the observable presentation Model interface with `presentation/tickets/viewmodels/TicketsViewModel.ts`, exposing display-ready state and `select/refresh/create/resolve` commands. The View binds to that state and invokes commands directly; subscription cleanup still exists. Gateway, browser operation contracts, backend and ticket rules stay unchanged. Headless presentation testing becomes convenient; binding/state mapping adds cost for this small screen. This is a real relationship change, not renaming the Controller or calling every Hook a ViewModel: `architecture/patterns/presentation/model-view-viewmodel/README.md`, “Mental model and roles” and “Fit and cost.”

Reject one `Port` interface per file: operations themselves are offered interactions; parsers, Views and formatters do not each need interchangeable abstractions. Keep only demonstrated capability boundaries. Also reject renaming the HTTP gateway Repository: these commands request remote work, while backend Repository models stored ticket objects. Sources: `architecture/foundations/dependency-boundaries.md`, “Ports model capabilities, not files”; Repository guide, “Repository, reader and gateway.”
