# H2 architecture scheme

The repository has real consumers and replacement pressure: creation stores tickets and resolution loads and conditionally saves them. It is not generated table CRUD. Its create-once extension records the new ticket and a bounded request receipt atomically; resolution compares the loaded revision when saving. No generic service container, domain service, event bus or distributed infrastructure is justified. C: `architecture/styles/hexagonal-architecture/README.md`, “Offered and required interactions,” “Placement and dependency decisions”; `architecture/patterns/persistence/repository/README.md`, “The interaction,” “Who owns what?” These support the boundaries, not these particular concurrency methods.

**Identity and authorization (I).** Actual ticket visibility rules are unspecified. Adopt a provisional single-service policy: authenticated analysts may create and access that service's tickets; operators need explicit equivalent grants. `TicketAccess` checks membership, action grant and the ticket's service boundary, rather than accepting an ID as permission. No tenancy product is invented. A narrower ownership policy would change this owner and scoped queries. Delivery establishes identity from verified credentials; application enforces resource policy. Recheck mutable access facts within the write consistency boundary, or include their revision in the conditional write. This extends `architecture/api-design/security-and-tenancy.md`, “Identity and permission” and “Scope every object,” without importing its scheduling-specific organization model.

MVVM's Model here comprises data and application capabilities, not a mandatory domain entity. Domain is deliberately absent in the browser: the backend owns persisted rules; client blank-subject feedback and a disabled resolve button are presentation conveniences. Decline a separate screen Facade. Selection is state directly owned by this ViewModel, and the Model already provides one adequate interaction contract; there are no independent selection/cache subsystems requiring a new coordinator. ## One contract, three relationships, complete operation

Proposed wire contract (I): list/get ticket representations contain `id, subject, status, revision`. POST creation accepts only subject plus a request key and returns the created representation. POST resolution accepts an expected revision and returns the resolved representation. Invalid shape is 400, invalid subject 422, missing authentication 401, denied action 403, hidden/unavailable ticket 404, stale revision or invalid transition 409, temporary storage failure 503. Failure bodies expose stable codes without database details. This is an operation-oriented HTTP API; no REST conformance claim. Server mapping and client parsing share a reviewed contract definition, not domain/database classes.

**Source:** backend delivery imports the application public entry; operations import Domain and their repository contract; the database adapter imports that same contract. Browser Views import feature presentation contracts; ViewModel imports application contracts; HTTP adapter implements those contracts. Type-only imports obey the same restrictions. **Runtime:** View invokes ViewModel, which calls supplied Model adapter; HTTP handler invokes supplied backend operation, which calls Ticket and supplied repository object. Interfaces are not runtime forwarding hops. **Composition:** separate browser, HTTP and CLI roots choose and inject implementations. C: `architecture/foundations/dependency-boundaries.md`, “Do not confuse runtime flow with source dependency,” “External technology types stop at the boundary”; `architecture/foundations/composition-root.md`, “Inject capabilities, not global bags,” “Framework bootstrap belongs at the edge.”

**Resolve trace (I).** The View forwards resolve for selected ID/revision. ViewModel records that immutable target, marks that row pending and calls the Model. HTTP adapter sends the command. Server verifies identity, rejects malformed fields, then `ResolveTicket` performs scoped load and authorization. Domain rejects resolved state; otherwise it produces resolved state. Conditional save compares the loaded revision atomically and increments it. Exactly one of two concurrent resolutions can commit; the loser receives conflict, even if both initially read open. Application owns this consistency requirement; the adapter implements it using the selected database's verified transaction/conditional-update facilities.

A known save failure returns an application failure; transport mapping cannot report success before commit. On success ViewModel installs the returned revision, refreshes affected data and keeps selection by ID. On conflict it reloads and explains the changed ticket. A network timeout after commit is an unknown outcome: preserve pending target, fetch its current state and display “resolution outcome unknown” until reconciliation succeeds. Seeing resolved establishes current state, not which actor resolved it. Do not automatically issue another resolve; a separate subsequent attempt encounters the authoritative resolved rule.

**Create retry (I).** Generate one request key per user intent and retain it with that draft until settled. Scope receipts to trusted actor and create operation; store normalized-subject fingerprint and result with the ticket in one transaction under a unique key. Identical concurrent requests serialize and replay the committed result; different payload under that key conflicts. An in-progress duplicate waits within a bound or returns retry-later without another insert. Retain receipts for a documented 24-hour retry window; clients stop automated retry at expiry and require reconciliation before a new intent. Reauthorize receipt replay; never reveal a result to another principal. Rollback removes both records. This is proposed application behavior, not an exactly-once network guarantee. C: `architecture/api-design/reliability-and-operations.md`, “Retries and duplicate requests,” “Timeouts and partial failure,” “Optimistic concurrency.”

Selection and feedback last for the screen; drafts last for the form. No URL persistence, global store or browser storage is required. Server rows are snapshots with explicit freshness, not client authority. Request generations discard late refresh responses, including reads started before mutation; abort on replacement/unmount supplements that guard. Serialize mutations per ticket and prevent duplicate form submission; a later selection must not receive an earlier target's error. Initial loading, empty success, retained stale rows during refresh, refresh failure and mutation failure have distinct states. Refresh failure never becomes empty success. Preserve keyboard selection, semantic buttons, focus on failed subject input, and accessible pending/error announcements. C: `architecture/frontend/state-management.md`, “Assign state by responsibility,” “Server state vs. application policy,” “Forms are not global state by default.” Specific race handling is I.

## Onion challenge and proposed evidence

Onion would add an explicit domain-centered inward-dependency constraint around the browser. MVVM still governs View/ViewModel interaction. The present client already separates presentation and HTTP integration through an inward-owned contract; renaming gateway to repository, or folders to rings, changes no behavior. A substantive Onion adoption would identify actual reusable client policy, place it in Domain, make Application coordinate it, and forbid outer imports inward. No such policy exists here. Decline adding a client Ticket class merely to fill `domain/`: copying server transition rules creates drift and a false authority. Reconsider when independent client policy emerges. C: `architecture/styles/onion-architecture/README.md`, “Fit and cost,” “Rings and responsibilities,” “Trade-offs and failure modes.”
