# L2 — public sales reporting design

**Decision and evidence.** Requirements: one public, read-only reporting product, date/category filters, pagination, empty/error states, one maintained SQL report store; Layered backend with Dependency Inversion and an interactive MVVM browser; responsive, keyboard accessible, light/dark/system. There is no application, schema, approved stack or executable evidence. This is a proposed scheme, not implementation approval or executed validation. H is the controller-exported handbook at pinned revision `d9a861cc7189ac988ed03e133ce6c765047afaf6`; its provenance is the supplied receipt, not an independently resolved Git HEAD.

**Basis labels:** R = application requirement; C = handbook convention; I = design inference. All proposed filenames, contracts and numerical limits below are I. Layer-first paths adopt C, not framework requirements. `architecture/foundations/architecture-design-review.md`, “Establish the decision and evidence” and “Describe owners and supported interactions,” require these distinctions and inspectable owners. `README.md`, “How to use the handbook,” identifies documentation rather than an executable application.

## Contracts and three relationships

**One proposed public contract (I):** `GET /api/sales-report?from=YYYY-MM-DD&to=YYYY-MM-DD&category=…&page=1&pageSize=25`. Both dates are inclusive report calendar dates in a documented store reporting zone; translate to `[start, next-day-after-to)` instants. Initial omitted dates mean all recorded dates, category omission means all categories; page defaults to 1, size to 25, maximum 100. Reject malformed/duplicate recognized parameters, reversed ranges and invalid pagination. Unknown category produces an empty report. These conventions must be approved with report-zone/currency semantics before implementation.

Success: `{items:[{productId,productLabel,currency,totalDecimal}], page,pageSize,totalItems}`. Rows represent product/currency groups, sorted by stable `(productId,currency)`; decimal strings preserve SQL precision. There is no cross-currency grand total. Totals are per group over the entire filtered range, never sums limited to one page. Out-of-range pages return empty items plus totalItems. DTOs belong to backend HTTP and frontend HTTP integration; internal `ReportPage` is separately owned even where shapes coincide. `architecture/foundations/code-placement.md`, “Where does a type belong?”, explains why matching shapes do not imply matching authority.

`ReportQuery` is normalized and semantically valid. `SalesReportReader` returns a `ReportPage` or typed unavailable/deadline failure; SQL defects remain unexpected faults. The operation may return invalid-query or unavailable outcomes; HTTP maps invalid queries to 400, known temporary unavailability to 503 and unexpected defects to sanitized 500. Errors use Problem Details with stable type/category and no SQL text. Frontend maps these into invalid-filter, unavailable or invalid-response states, never exposes raw status codes as the ViewModel's API. These are I informed by `architecture/api-design/resources-and-operations.md`, “Collections and time” and “Error contract.” This is an HTTP query interface; no claim of complete REST conformance.

**Source imports:** backend Application → its own contracts/Domain; SQL adapter → Application port/Domain; handler → Application entry; Domain → pure Domain. Browser View → presentation contract; ViewModel → client contract and feature state; HTTP integration → client contract. Only composition imports implementations for assembly. Type-only imports, reexports and dynamic imports count. Cross-capability callers use explicit entries. These constraints adopt `architecture/foundations/dependency-boundaries.md`, “A practical four-area mapping,” and `architecture/foundations/module-boundaries-and-public-apis.md`, “Public API per non-trivial module” and “Barrels are contracts, not export dumpsters.”

**Runtime:** View command → ViewModel → supplied HTTP client → handler → GetSalesReport → supplied SQL reader → SQL. Returned facts flow back into ViewModel state and rendering. The inward contract is not a forwarding runtime object. **Startup:** each executable constructs its concrete graph once; no inner module locates a container. Manual wiring is sufficient (`architecture/foundations/composition-root.md`, “A DI container is optional”; dependency guide, “Do not confuse runtime flow with source dependency”).

## Operation, failures and browser lifetime

Initial route parsing establishes the applied query and initializes draft fields. Editing draft changes no URL, result or request. Apply validates feedback, resets page to 1 and commits one normalized URL transition; URL synchronization initiates exactly one load. Back/forward replaces applied query and draft from URL, then loads. Invalid URL shows actionable field errors without querying. Retry reloads the current applied query without adding history.

The route-scoped ViewModel owns draft/applied filters and asynchronous state; only the URL persists applied filters beyond that lifetime. Server facts remain server-owned. No global cache/store or local draft persistence is needed. Each load increments a generation and cancels its predecessor; only the current generation/query may commit success, error or loading completion. Dispose cancels and invalidates generations, preventing late unmounted updates. Initial loading shows progress; on query change old rows are cleared so they cannot appear under new filters. Empty success differs from unavailable error. Current failed query stays in URL, allowing Retry. See `architecture/frontend/state-management.md`, “Assign state by responsibility,” “Start with capability-owned state” and “Forms are not global state by default”; MVVM guide, “Mental model and roles,” establishes state/command binding rather than a renamed DTO.

Backend parses and validates independently, evaluates report rules, then performs the aggregate/page/count within one database read snapshot. Reader owns the SQL mechanism; its port promises internally consistent page/count. This requires verification against the selected database's actual isolation and refresh behavior. Across separate page requests the report is a moving view: external refreshes may change counts and shift rows despite stable ordering. Snapshot browsing would require an explicit dataset revision contract; it is not silently promised.

There are no authenticated identities or editable resources (R); public report authorization is an explicit allow decision, not trust in caller-supplied identity. The SQL account is read-only and HTTP exposes no writes or arbitrary SQL. No optimistic write conflict or idempotency-key mechanism is needed. Browser preferences/URL changes are local state changes; unknown network outcomes are repeatable reads, not uncertain business mutations. Deadlines/cancellation bound work; timeout does not imply SQL stopped. Retry can observe fresher facts. This proportional application follows `architecture/api-design/reliability-and-operations.md`, “Retries and duplicate requests” and “Timeouts and partial failure.”

ThemeState owns `light|dark|system`; system mode alone follows media changes. `tokens.css` maps semantic canvas/text/error/focus roles to primitives; component modules consume them. One document theme attribute is synchronized by the shell binding. Label controls, preserve visible keyboard focus, announce loading/result/error status politely, associate validation messages, and provide semantic table headers/caption. Apply keeps focus on its control or first invalid field; page changes announce page/results without unexpected focus jumps. Narrow layouts stack filters and permit labeled table scrolling. Named breakpoints follow real layout transitions. Source: `architecture/frontend/styling-and-design-system.md`, “Semantic tokens,” “Global styles have one owner,” “Keyframes and reduced motion” and “Responsive design”; these support ownership principles, not a mandate for Panda.

## Alternatives, challenge and proposed checks

**MVC alternative:** replace the browser ViewModel with `presentation/reporting/state/ReportModel.ts` owning observable query/results, plus `controllers/ReportController.ts` interpreting Apply/page/retry gestures. Views subscribe, read Model state and unsubscribe on removal; Controller invokes Model operations. Move generation/cancellation into Model, URL gesture interpretation into Controller, retain transport behind the injected client. The backend is unchanged. This adds observer/controller wiring; MVVM more directly fits R's explicit state/commands. Server-rendered MVC would instead submit filters to a controller selecting an HTML view and requires a deliberate product/interactivity redesign. Neither a JSON handler nor React automatically constitutes MVC. Source: `architecture/patterns/presentation/model-view-controller/README.md`, “MVC across client and server,” “Mental model and roles” and “Trade-offs and failure modes.”

**Remove the inward-owned reader?** A viable ordinary Layered alternative has GetSalesReport import a data-access-owned `SqlReportQueries` API; startup supplies that concrete dependency, and Application now accepts outward source coupling. Move/rewrite reader types and failure mapping, update imports/structural rules and test seams; do not merely delete `implements` while keeping an Application-owned structural contract. Runtime can remain identical. Less abstraction costs harder SQL/API substitution and no longer satisfies assigned DIP. Retain the narrow port for R; this is Layered with DIP, not proof of a full Hexagonal/Clean architecture. A report reader returns aggregated projections, not collection-like stored business objects, so calling it Repository is misleading (`architecture/patterns/persistence/repository/README.md`, “The interaction” and “Repository, reader and gateway”).

All following checks are **proposed, unexecuted**:

| Change/boundary | Observable positive and negative evidence |
| --- | --- |
| Rule changes to exclude a defined sale classification | Change `ReportPolicy.ts`, reader query and fixtures; valid included records sum exactly, excluded records do not. Client/parser remain stable unless report meaning requires a versioned contract change. This rule necessarily affects SQL: projection execution cannot be insulated from changed selection semantics. |
| SQL schema/driver replacement | Change SQL reader/query and bootstrap; contract suite returns identical decimal groups/page counts. Driver-shaped records cannot escape; real integration rejects injection-shaped category input and verifies consistent count/page during refresh. Memory fakes establish neither SQL isolation nor refresh safety. |
| Additional CLI caller | Add `presentation/cli/reporting/ReportCommand.ts` and its root, consuming Application entry; valid normalized query works, reversed dates fail without HTTP. No SQL private import or duplicated rule. |
| Browser concurrency/integration | Delay A, finish B, then resolve/reject A: only B renders; dispose commits nothing. Invalid payload becomes invalid-response; Retry sends applied filters, never unapplied draft. Back/forward restores URL state once. |
| Structural and visual boundaries | Accept SQL adapter → Application port and ViewModel → client contract; reject Application → SQL type-only import/reexport/dynamic import and View → HTTP implementation. Keyboard-only operation, narrow viewport, all themes and system changes preserve focus/readability and distinguish empty/error/loading. |

Change simulation follows design-review “Challenge the design before accepting it”; check separation follows `architecture/foundations/architecture-testing.md`, “AST-based tests” and “Test behavior and boundaries separately.” Verdict: coherent proposed design subject to unresolved reporting semantics, schema/refresh guarantees and runtime selection; no build, security, isolation or accessibility result is claimed.
