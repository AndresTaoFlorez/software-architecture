# Expense approval scheme — C2

**Status: design only.** No application, approved technology stack, schema or tests exist. No implementation or application check was executed. Reference H is the controller-exported handbook at revision `1c9deb1558b9d50737d6979dabab308350468c67`; its provenance is the supplied receipt, not an independently resolved Git HEAD.

**Requirements (R):** employees submit positive expenses; only designated reviewers approve; nobody approves their own submission; persisted status uses revision checks; duplicate/concurrent approvals cannot corrupt state. ## Owners and physical map

Paths below are proposed under `backend/src/` or `frontend/src/`; braces enumerate artifacts, not extra architectural layers.

| Backend path | Authoritative responsibility and supported consumers |
| --- | --- |
| `domain/expenses/{Expense,Amount,ApprovalPolicy}.ts` | `Amount` accepts a finite positive decimal; `Expense.submit/restore/approve` own submitted→approved and no-self-approval. `ApprovalPolicy` checks actor against supplied designation facts. Application and adapters use the public domain entry; no HTTP, ORM or startup imports. |
| `application/expenses/use-cases/{SubmitExpense,ApproveExpense,GetExpense,ListReviewExpenses}.ts` | Coordinate trusted actor, access, rules, consistent persistence and results. HTTP or future CLI uses `application/expenses/index.ts`; no framework or adapter imports. |
| `application/expenses/contracts/{commands,results,failures}.ts` | Own operation inputs, `ExpenseResult`, typed failures and trusted `ActorContext`; exclude browser/ORM objects. Public entry exports supported contracts, not private helpers. |
| `application/expenses/ports/{ExpenseStore,ReviewerAssignments}.ts` | Store supports creation, authorized reads/listing and a transactional approval session. Assignments supplies server-controlled designated reviewer IDs for submission; it cannot trust body claims. Concrete adapters implement these required capabilities. |
| `presentation/http/expenses/{ExpenseController,dto,parsers,mappers}.ts` | Routes, unknown-request validation, command construction and public response/error mapping. Imports Application public entry; cannot import persistence. |
| `presentation/http/security/Authenticate.ts` | Verify chosen credential and create trusted actor; never accept actor/employee/reviewer privileges from JSON. Cookie deployment also needs CSRF protection. |
| `infrastructure/persistence/expenses/{SqlExpenseStore,mapExpenseRecord,schema}.ts` | Database transaction, conditional write, constraints and stored/domain translation; schema owns unique ID, positive amount, status/revision and approval metadata consistency backstops. |
| `infrastructure/reviewers/ConfiguredReviewerAssignments.ts` | Proposed trusted configuration integration for designation. Actual administrative source remains unresolved; no reviewer-management feature is invented. |
| `composition/bootstrap.ts` | Construct credential adapter, store, assignments, operations and delivery routes; inject them. No business decisions here. |

This maps Clean Entities to Domain, Use Cases to Application, Interface Adapters to transport/storage translation, and Frameworks/Drivers to outer HTTP/database glue. No requirement for one directory per conceptual circle follows. Basis: H `architecture/styles/clean-architecture/README.md`, “What each circle owns”; H `architecture/foundations/code-placement.md`, “Responsibilities”, “Where does a type belong?” and “Parsing and mapping follow the boundary”. Store abstraction protects actual transaction substitution, not merely a table; it is deliberately named Store rather than promising collection-style Repository semantics.

**I:** choose open responsibility layering with dependency inversion: Presentation imports its own pieces and Application public contracts (pure Domain values only where needed); Application imports Domain and its required gateway; Infrastructure imports inward contracts; Domain imports no outer layer. Presentation never imports Infrastructure or a container, including type-only imports. Runtime calls can travel outward through supplied objects. Startup alone imports concrete implementations. This is a specified project policy, not an inherent rule of every Layered design: H `architecture/styles/layered-architecture/README.md`, “Specify how layers may interact” and “Ticket variation with Dependency Inversion”; H `architecture/foundations/dependency-boundaries.md`, “Do not confuse runtime flow with source dependency”; H `architecture/foundations/composition-root.md`, “Keep composition out of inner modules”.

No global store/cache, shared UI package, separate domain service framework or server ViewModel is needed. The form draft lives until submission/navigation; selection and rows live with the review route, with selected object derived from selected ID and current rows. No URL persistence is required. Browser rows are snapshots, never authoritative state. Component styles remain local; appearance/theme is outside this task. Basis: H `architecture/frontend/state-management.md`, “Assign state by responsibility”, “Selectors own derivation”, “Forms are not global state by default”; H `architecture/frontend/presentation-architecture.md`, “Component colocation”, “Avoid the God ViewModel”.

## Contracts and operation trace

**I: one transport agreement**, owned by backend HTTP delivery and mirrored by the client integration, independent of Application/ORM types:

| Interaction | Input → output; meaningful failures |
| --- | --- |
| `PUT /expenses/{clientChosenId}` | Submission `{amount: decimalString}`; employee ID comes from authentication. First create returns 201, same actor/ID/same original payload replay returns 200 current resource; differing payload/owner cannot overwrite. |
| `GET /expenses/{id}`, `GET /review-expenses` | Authorized snapshot/list `{id,amount,submitterId,status,revision,approvedBy?}`; list includes only designated resources. Empty list is successful. |
| `PUT /expenses/{id}/approval` | `{expectedRevision: nonnegativeInteger}` → 200 updated snapshot. Actor omitted from body. No general status PATCH. |

HTTP parser rejects malformed/unknown fields (400); unauthenticated 401; forbidden operation 403; missing/invisible object 404; stale revision or already-approved transition 409 with distinct machine codes; positive-amount business failure 422; unavailable persistence 503. Transport unavailability/timeout means **unknown outcome** for a mutation. Client parser failure means unusable response, not proof of rollback. Application failures contain semantic codes, not HTTP/database exception types. Amount precision/maximum and credential mechanism require product/stack decisions before implementation; no binary-floating arithmetic or framework/version guarantee is assumed.

Submission operation obtains trusted assignments, constructs a valid submitted expense, and inserts once with revision 0. Original submitter/payload fingerprint is retained for repeatable creation; a unique expense ID closes simultaneous-create races. Same-payload replay must not reset an already-approved resource. Assignment-source failure writes nothing. These are proposed mechanisms for safe submission reconciliation, not requirements supplied by H.

Approval runtime: View gesture → `ReviewExpensesViewModel.approve` → frontend `ApproveExpense` → supplied `HttpExpenseGateway` → network → authentication/parser/controller → backend `ApproveExpense` → supplied store transaction. Application loads expense and current designation facts inside that transaction, checks resource authorization and expected revision, asks Domain to approve, then saves conditionally on ID/revision/submitted status. Successful update increments revision exactly once and records approver; commit precedes response. A zero-row conditional update becomes a conflict, never an overwrite. Storage/session operations expose domain snapshots and commit outcomes, not transaction-client types.

**I:** designation is persisted with the resource; any future designation modification must increment the same revision or participate in the same locking protocol. Thus revocation cannot race an approval based on earlier facts. Approval is terminal in this scope. Application owns transaction scope; adapter implements atomicity, rollback and known-failure translation. A fake store cannot establish these guarantees. Basis: H `architecture/api-design/security-and-tenancy.md`, “Identity and permission”, “Scope every object”; H `architecture/api-design/reliability-and-operations.md`, “Two bookings for one slot”, “Optimistic concurrency”, “Timeouts and partial failure”. No tenancy requirement is inferred from H's scheduling example.

Two approvals with revision 0 yield one committed revision 1 and one conflict, including duplicate clicks by the same reviewer. On lost response, keep outcome uncertain, reload the authorized expense and display its current state/approver. Retry may reuse the **original** revision; never silently fetch a new revision and reapply intent. An approved snapshot proves final state, not that this particular request caused it. Submission retry reuses original ID/payload. Neither operation promises exactly-once network delivery or requires distributed services/outbox/payment.

Browser load states distinguish initial/loading, ready-empty, ready, failed and stale-with-error. Each load has a generation; only the current generation publishes. Changing selection derives the summary from current rows; missing selection becomes null. Unmount releases subscriptions and cancels reads where possible; generation checks still reject late completions. Mutation tracks the captured expense ID/revision independently of later selection, disables duplicate approval and never paints another row's result. Older read results cannot replace a newer mutation revision. After conflict reload and request explicit review; after forbidden access clear protected data; failed refresh retains clearly stale rows. Cancellation does not imply server rollback. Labels, disabled actions, keyboard selection, focus retention and an accessible pending/error region belong to View/binding. H `architecture/patterns/presentation/model-view-viewmodel/2-the-binding.md`, “The MVVM cycle”, “What the binding replaces — and what it doesn't”, supports synchronization/cleanup, not race prevention by itself.

## Facade, alternative and challenged proposals

**I: the ViewModel also merits Facade semantics**, without a second wrapper. `load()` coordinates `LoadReviewSummary` and `ReviewSelection`, then offers rows plus the matching selected summary through one screen contract. List and summary consume it without knowing reader/selection collaboration. Reader failure remains failure rather than empty success. Selection mechanics remain privately replaceable; authoritative approval rules stay elsewhere. Remove the Facade label if it becomes only forwarding. Basis: H `architecture/patterns/structural/facade/README.md`, “Show the collaboration first”, “Name the pattern”, “Distinguish nearby roles”, “Change and verification”.

Plausible **interactive MVC alternative**: replace ViewModel commands with `presentation/expenses/controllers/ReviewController.ts` interpreting gestures, and represented state with `state/ReviewModel.ts`. View subscribes to Model notifications and reads state; Controller invokes Model/application behavior. Selection/busy/errors move into that represented Model, formatting remains View-owned, and cleanup/async policies remain necessary. MVVM instead binds View directly to screen-ready ViewModel state and commands; two-way binding is optional. Backend, gateway and business contracts stay unchanged. MVC adds explicit gesture ownership but more collaborators for this screen; reconsider if multiple Views naturally observe one represented Model. H `architecture/patterns/presentation/model-view-controller/README.md`, “Mental model and roles”, “MVC across client and server”; MVVM README, “Mental model and roles”, “MVVM across UI platforms and server code”.

Reject **ORM records as use-case outputs**: storage-owned fields/types couple protected operations and callers to schema, risk lazy-loading/serialization leakage and bypass intentional public-field selection. Adapter maps to Application-owned results; HTTP separately maps to wire DTOs. Identical shapes may use plain data/functions, not ceremonial classes. H `architecture/styles/clean-architecture/1-the-dependency-rule.md`, “Boundary data”; H `architecture/foundations/dependency-boundaries.md`, “Type ownership follows meaning”. Reject **mandatory server ViewModel**: browser MVVM does not prescribe server presentation. JSON delivery needs request/response mapping; a future HTML template could have page data without establishing interactive MVVM. MVVM README, “MVVM across UI platforms and server code”.

## Change probes and proposed checks — all unexecuted

| Pressure | Owners/contracts affected; observable positive and negative checks |
| --- | --- |
| Rule: disallow approval above a product-defined limit | Change backend `ApprovalPolicy` and rule tests, expose a semantic failure through existing result/error mapping; browser message may change, persistence/client cannot become authority. Positive: designated nonowner approves below limit. Negative: above-limit, zero amount, self-approval and nondesignee attempts leave status/revision unchanged, including direct Application calls. |
| Integration: replace SQL driver/schema | Change `SqlExpenseStore`, mapper/schema and startup only if port semantics remain achievable. Proposed real-database check: barrier-start two approvals, exactly one success/revision increment; inject rollback and lost-response scenarios, observe no partial status/approver state. Same ID submission replay preserves approval; altered payload cannot overwrite. Failure to reproduce atomicity invalidates adapter fit. |
| Additional caller: authorized CLI | Add CLI parser/authentication/mapper and composition supplying existing operations; no browser ViewModel import. Positive valid command follows identical rules; negative forged submitter/reviewer identity and invisible ID reveal no data/write. A new consumer's need for a different result should evolve an explicit supported contract, not export ORM records. |
| Browser/integration | Select A then B during reordered loads: only current rows/selection render. Approve A then select B: B never shows A's result. Test empty vs failed response, invalid DTO, timeout→reload, conflict→explicit review, unmount cleanup and keyboard/focus/feedback. Mutation stays uncertain until reconciliation, not falsely successful. |
| Source boundaries | Permit `ApproveExpense` importing Application `ExpenseStore`, and frontend gateway implementing Application contract. Reject Application importing SQL/ORM, View importing HTTP adapter, outward type-only import/reexport/dynamic literal import, and unrelated consumer deep-importing private selection. Resolve aliases; prohibit unresolved computed imports across boundaries. |

These checks distinguish business, integration, presentation, contract and structural evidence; none proves the others. Basis: H `architecture/foundations/architecture-testing.md`, “What to enforce”, “AST-based tests”, “Public API tests”, “Test behavior and boundaries separately”; H `architecture/foundations/module-boundaries-and-public-apis.md`, “Public API per non-trivial module”, “Barrels are contracts, not export dumpsters”. The scheme is coherent under its stated inferences; executable security, database behavior and accessible rendering remain to be verified after an authorized implementation and concrete stack decisions.
