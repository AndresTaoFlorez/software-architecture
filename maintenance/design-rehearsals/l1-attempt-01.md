# Public sales reporting: closed Layered backend and server-rendered MVC

**Evidence and basis.** Requirements [R]: public read-only product sales totals, date/category filters, pagination, empty/error states, one maintained SQL report store, closed Layered backend and server-rendered web MVC; no authentication, editable business objects or checkout. There is no application code, schema, accepted stack or test suite. Reference H is the controller-exported snapshot at `1c9deb1558b9d50737d6979dabab308350468c67`; its provenance is the supplied receipt, not an independently resolved Git HEAD. The three copied consumer skills were loaded. [C] below means handbook convention/principle; [I] means proposed application decision, including every proposed filename and contract. No application checks have run.

**Decision.** Use one executable with three responsibility layers: Presentation → Business → Data Access. Business combines modest reporting policy and application coordination; Data Access owns SQL and record conversion. MVC separates server controller, reporting model behavior and HTML templates; it does not create an observer-based browser model. H `architecture/styles/layered-architecture/README.md`, **“Specify how layers may interact”**, explicitly permits concrete downward dependencies in closed layering; its dependency-inverted variant is optional. H `architecture/patterns/presentation/model-view-controller/README.md`, **“MVC across client and server”**, describes controller-selected views consuming supplied data [C]. This costs a real Business boundary, justified by shared query policy and failure coordination rather than forwarding [I].

## Contracts and reporting semantics

The following are proposed decisions [I], pending agreement with the report-store owner; they are not inferred facts about an existing schema.

| Contract / owner | Input → output and failure meaning |
| --- | --- |
| HTML delivery / Presentation | `GET /reports/sales?from=YYYY-MM-DD&to=YYYY-MM-DD&category=…&page=…`. Date pair required together; absence means all maintained report dates. Optional category means all; page defaults to 1, fixed size 25. Success/empty: HTML 200; invalid query: HTML 400 with retained safe values/field errors; unavailable store: HTML 503 with same-query retry link; unexpected defect: generic HTML 500. No public JSON contract or REST claim. |
| `ReportQuery`, `ReportResult` / Business | Typed date strings and optional category ID, positive integer page → `success { normalizedQuery, rows, matchingProducts, filteredTotals, generatedAt }`, `invalid { fieldErrors }`, or `unavailable`. Enforce real dates, `from ≤ to`, bounded integer page/offset before I/O; unknown well-formed category yields empty, not an existence leak or failure. |
| `readReport(ReportRead)` / Data Access | Explicit normalized range/category/limit/offset → unformatted product projection, count and full-filter totals from one consistent read; typed `ReportStoreUnavailable` for known timeout/connectivity failure. Malformed stored values raise an integrity defect; they never become zero/empty success. No HTTP status in this API. |
| `SalesReportPage` / Presentation | Discriminated content/empty/invalid/unavailable/error render data; formatted amount strings, labels, selected query, next/previous URLs. No executable commands, driver fields or business eligibility logic. |

Define store grain before SQL: one maintained product/category/calendar-day sales projection, summed to one row per product for the requested interval/category. Total means the full filtered dataset, not the visible page. Use an explicit reporting calendar/time zone and documented net/gross/cancellation treatment supplied by the store's business definition; do not silently choose these accounting meanings. If amounts span currencies, return separate currency totals rather than add them. Preserve exact decimals through SQL/mapping and format at display; never binary-float aggregate [I]. These semantic uncertainties block implementation of aggregation, not this placement decision.

Proposed ordering is immutable product ID ascending; page beyond the last yields empty with a previous link. Parameterize every filter and allow no client-controlled SQL identifiers. Fetch page/count/totals in a single statement snapshot, or a read-only transaction with verified snapshot semantics if several statements are necessary. Data Access owns that mechanism and cleanup; Business owns operation timeout/failure policy. SQL engine/isolation guarantees remain conditional until integration-tested [I]. H `architecture/patterns/persistence/repository/README.md`, **“Change and verification”**, warns that an in-memory substitute proves neither database transactions nor durability [C].

## Imports, calls and assembly

**Source permissions [I]:** Presentation imports Business's public `GetSalesReport`/query/result API; Business imports Data Access's public reader/read contracts, intentionally downward; Data Access imports its driver and own helpers. Presentation must not import Data Access, even type-only, via reexport or dynamic import. Templates have only Presentation render types. Lower layers never import upper layers or composition. No container lookup. Composition alone may import all construction APIs.

**Runtime:** controller → supplied `GetSalesReport.execute` → supplied `SqlSalesReportReader.readReport` → SQL → Business result → controller/page mapper → template renderer → HTML. A runtime call reaches SQL without authorizing a controller SQL import. **Startup:** `startServer.ts` supplies pool to reader, reader to operation, operation/renderer to controller, then registers routes. A plain injected instance is sufficient; no inward port or DI container is added. H `architecture/foundations/composition-root.md`, **“Composition is a boundary, not business policy”**, **“A DI container is optional”**, and H `architecture/foundations/dependency-boundaries.md`, **“Do not confuse runtime flow with source dependency”**, support these distinctions [C].

## Operation, browser state and failure trace

1. Browser displays URL-selected dates/category/page; unsubmitted edits live only in native controls. Submit is a native GET form with page omitted/reset to 1; pagination preserves applied filters in escaped, encoded URLs. URL owns applied query lifetime; Business/report store owns facts; request-local page data owns rendering. Back/forward restores document/query; a displayed report is a snapshot, not a live subscription [I].
2. Controller parser rejects malformed/repeated fields before invoking Business; direct non-HTTP callers still receive Business semantic validation. Valid query reaches reader; category/date predicates constrain rows before aggregation, totals and pagination. Reader parses unknown SQL results, then Business returns success. Mapper formats and renderer emits semantic table/caption, labelled filters, headings, error summary and previous/next links.
3. Empty result displays explicit “No sales match these filters”, preserving controls; it never disguises timeout. SQL timeout becomes `unavailable`, then 503; defect becomes generic 500 with server-side correlation logging, not SQL/credentials in HTML. Validation errors link to labelled fields. Keyboard navigation and visible focus must remain usable. New-document headings/title communicate result state without pretending a live region announced a page load [I].
4. Native navigation owns loading/cancellation; current page remains while a navigation waits. There is no custom asynchronous response-to-state race. Closing/leaving the request may cancel the query if the chosen driver supports it; otherwise bounded execution and connection cleanup still apply. Failure before HTML receipt has an unknown *read* outcome: repeat the same GET; there is no mutation to duplicate and no idempotency record needed. Disable application result caching initially; browser history may show older HTML, so show generation time and a reload link [I].

Public resource access needs no trusted end-user identity or per-user authorization [R]. Only approved aggregate projections are exposed; client-supplied identity fields grant nothing. Database credentials are server configuration with read-only privileges. No write routes or write capabilities are registered. Concurrent maintenance of the SQL store must not tear one response's page/count/totals. Separate navigations can legitimately see refreshed data and shifting page membership; cross-request snapshot continuity is not promised [I]. H `architecture/foundations/architecture-design-review.md`, **“Trace behavior across boundaries”**, supports proportionate failure/concurrency analysis [C].

## Alternatives, change pressure and proposed evidence

| Challenge | Decision, cost and reconsideration |
| --- | --- |
| Open layering | Could permit controller → reader for pure projections, saving a Business hop. Here it would duplicate normalization, result semantics and failure coordination across callers. Retain closed requirement; revisit only with explicit requirement change and a reader API that already owns the shared policy. H Layered guide, **“Specify how layers may interact”**, **“Fit, cost and change”** [C/I]. |
| Repository per report table | Reject: tables represent storage, not collection-like business objects. One purpose-specific reader owns aggregation across the maintained store; no generic CRUD. Reconsider if real object lifecycle/persistence interactions emerge. H Repository guide, **“The interaction”**, **“Repository, reader and gateway”**, **“Change and verification”** [C/I]. |
| Pass-through Facade | Reject a second object forwarding `execute` unchanged. Current operation performs policy/coordination; page mapper performs display translation. Reconsider a facade only when callers repeatedly coordinate several capabilities. H `architecture/patterns/structural/facade/README.md`, **“Name the pattern”**, **“Distinguish nearby roles”** [C/I]. |

The scheme is coherent subject to agreeing report semantics and verifying SQL/runtime behavior. It establishes neither running software nor executed security, accessibility or database guarantees.
